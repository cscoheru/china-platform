### 4.3 架构师裁定: 不新写 016 migration

639 tasking 草稿建议 016 migration 加 `policy_document.is_demo` / `government_commitment.is_demo` / `project_event.is_demo` 独立 BOOLEAN 列(类比 015 person.is_demo / appointment_event.is_demo)。640 架构师裁定:

- **沿用 009+010 lineage JSONB sentinel**,**不新写 016 migration**
- 理由 1: lineage JSONB 是 docs/33 §3.2 规定的 is_demo 唯一落点;015 偏离 sentinel 是因为 person / appointment_event 两表 schema 无 lineage JSONB(009 加 lineage 时这两表不在 5+1 政策表之列),是历史债
- 理由 2: 6 张政策表已经有 lineage JSONB + GIN 索引,功能等同独立 BOOLEAN 列,查询性能满足 `WHERE lineage->>'is_demo' = 'true'`
- 理由 3: 维护成本:加列易回退难;沿用 sentinel 一致性更高

如果 641 或后续刀需要更高频查询 is_demo (e.g. join 多表过滤),可考虑 expression index:
```sql
CREATE INDEX idx_*_is_demo ON tbl ((lineage->>'is_demo'));
```
但目前 lineage JSONB GIN 已足够,不在 640 范围。
